# BCENV-012: six-hour continuity and capacity feasibility

Prospective design, 2026-10-22. No012 candidate or engineering preflight has
started. The competitive goal remains unmet. Existing-VM engineering continues
under the standing mandate: no new spending, merge permission, access relaxation,
prior competitor resumption or strategic coaching.

## Question and limits of the comparison

The preceding short-run profile capped each fresh author at45 minutes and eight
training versions. It exercised bounded scrimmage learning, but did not test a
single author's sustained development over hours. Public code/process evidence
also distinguishes test execution from correctness; more receipts alone are not
competence. This pilot asks whether one fresh author can maintain a useful,
source-bound learning process over a longer bounded native session and produce
a legal selected artifact for independent evaluation.

This is a **bundled continuity/capacity feasibility experiment**, not a causal
duration test or a claim that insufficient time caused earlier results. Time,
version, note and replay budgets increase together. The public opponents,
training/validation schedules, engine, match rules, tools and requested model
remain fixed. We do not add bot fixes, tactical lessons, a hidden-panel-derived
curriculum, mandatory instrumentation or another agent's implementation.

## Separately versioned, opt-in profile

`continuity-v1` is a trusted-operator configuration, not a candidate option.
Missing profile preserves the old defaults. Unknown profiles and contradictory
explicit quotas fail closed. The resolved profile is part of launch parity.
The implementation is [bcenv draft PR24](https://github.com/anicolao/bcenv/pull/24),
stacked on PR23; its installed engine/adapter closure remains unchanged while
the separately hash-bound host service implements the profile and accounting.

| Bound | Continuity profile |
| --- | --- |
| Service clock |21600 seconds from initialization; no reset/extension |
| Training |24 source versions maximum, eight fixed games each;192 games maximum |
| Selection validation |Exactly two locked original finalists, eight conditions each;16 games maximum |
| Total games |208 maximum; not a completion promise |
| Source-bound notes |72 shared across phases |
| Replay queries |450, also charged to shared reads |
| Shared reads |2000; polling and status reads consume this budget |
| Mailbox requests |2200 including invalid attempts as defined by the service |
| Concurrency |One worker; at most two accepted versions pending |
| Match run |Engine and initial replay summary each at most300 seconds |
| Other child operations |Existing120-second limits |

All service child operations are clipped by the **same remaining global
deadline**, not supplied extra time. Existing request, response, source, output
and replay-page limits remain unchanged. Quotas are maxima, not entitlements to
finish work. Consuming450 replay queries leaves at most1550 other shared reads;
excessive polling can exhaust the interface before the wall deadline. Invalid
requests are not free. No retries after an uncertain request outcome.

The service detects and refuses further work when its configured owned roots
exceed a1GiB logical-file high-water threshold, checking before and after bounded
work and final selection. **This is not an OS disk quota:** an in-flight bounded
operation may overshoot. Exact covered roots, symlink policy, observed byte
counts and excluded temporary/candidate workspace storage are recorded in the
implementation and readiness evidence. No whole-VM disk-confinement claim is
made. Existing payload/process bounds remain necessary alongside detection.
Scans are not atomic. A concurrent temporary-file change can produce a scan
failure and conservatively halt below the threshold; this is an explicit
liveness risk, not proof the byte limit was exceeded. No scan retry or resumed
trial is implied by recording that distinction.

## One fresh author, not a succession of coached retries

- Request gpt-6.1-sol/high with fork-none and an exact self-contained kickoff.
  Record requested settings, not an independent runtime-model attestation.
- Give the general goal, public rules/API, fixed helpers, interface/budget
  semantics and boundaries. The author chooses its own strategy, milestones,
  hypotheses, tests and experiments. No prior source, reviews, outcomes,
  evaluator information or operator-authored bot lessons enter the export.
- Start the hard clock with live service initialization. Immediately inspect
  remaining time; service-to-spawn delay is consumed budget. No mid-run reset.
- Keep source snapshots, concise prospective notes, actual test evidence and
  replay references. Maintain a concise own `work/CHECKPOINT.md` (at most32KiB)
  at self-chosen milestones, identifying source/submission IDs, completed and
  pending work, supported/untested claims and next self-chosen questions.
  This is a work artifact, not a request for private chain of thought.
- Same-author automatic context compaction is compatible with continuity.
  Checkpoints permit rereading one's own work, not replacement of the author,
  resumption after worker/session loss or restoration of a lost service clock.
- At legal early completion, stop; six hours is a maximum, not forced activity.
  Infrastructure failure, run halt, uncertain outcomes or native/session loss
  end the run without a replacement or repaired attempt. A reached operation
  quota adds no allowance, but does not by itself invalidate earlier work or
  prohibit a still-legal finalization. Exhausted reads/mailbox capacity can make
  finalization impossible; that is incomplete, not an entitlement to more calls.

The exposed native spawn contract has no duration parameter or documented short
cutoff. The [matching official multi-agent guide](https://developers.openai.com/api/docs/guides/responses-multi-agent)
documents independent automatic compaction of agent contexts. This supports a
continuity experiment, **not a guarantee of six-hour uptime**, context fidelity,
unlimited execution or persistence across VM reset. No new API/CLI route is
introduced to obtain longer execution.

Native tools retain wider physical access. Workspace-only instructions and
observed conformance are a cooperative boundary, not hard filesystem isolation
or a complete access audit. The candidate may not inspect siblings, services,
other agents, reference sources, connectors or the web, spawn agents, change
fixed inputs, or manipulate the mailbox outside the supplied client.

## Unchanged locked selection

Training uses the same eight public conditions per version as011. Rejected
builds consume a version without games. After pending training finishes, lock
exactly two distinct completed verified original training IDs and a provisional
choice **before** any validation feedback. The lock permanently closes training:
no edits, submissions, re-nomination or second validation batch.

Both immutable versions receive the same eight public validation conditions.
The deterministic public-map rule excludes only training maps, not hidden-panel
membership. Only after both complete may the author select one original locked
ID, restore those exact source bytes and stop. Preserve separate training and
validation results; neither is an independent held-out estimate. Incomplete
validation means no legal final selection, no fallback and no private evaluation.

## Measurements and stopping rules

At launch, hourly service-clock milestones and final stop, record elapsed and
remaining time, observed native status, version/note/read/replay/mailbox counts,
phase and pending work, attempted/completed games, storage samples/high-water
events and existing checkpoint-file hashes. Hash only bounded regular checkpoint
files without following symlinks; a missing/oversized/unstable observation is
recorded as such, not backdated. Observer records stay outside candidate inputs.
No polling or milestone observation creates a new game or tactical message.
Transport mailbox attempts are counted separately from dispatched operations;
malformed transport inputs can consume an attempt without reaching dispatch.
Use existing candidate status receipts with their as-of timestamps, documented
reconstruction, or an explicit unknown value; do not equate successful audit
events with all debits. Observer milestones do not inject mailbox queries or
consume candidate quotas. The opt-in existing status response reports aggregate
used allowances; it adds no new operation, tactical signal or correctness oracle.

Final evidence includes learning-cycle chronology, source-bound hypotheses and
replay references, meaningful executed checks and preserved failures, selection
legality, code quality and separately measured performance. Record observable
continuity interruptions without inventing token/compaction/retention telemetry.
More elapsed time, versions or well-formatted records do not themselves establish
competence. One author is not a reliability distribution or a causal comparison.
