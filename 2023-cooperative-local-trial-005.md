## Question and environment changes

Can the practical cooperative environment support an independently observable
learning loop with stronger public development exposure, immutable pre-result
experiment notes, and actual candidate-authored Java tests? BCENV-004 showed a
functioning service but weak diagnostic generalization and partial narrative
chronology. This bundled exploratory iteration cannot isolate the causal effect
of any one environment change.

- Mandatory source-bound experiment-note receipts before submissions; prior
  replay references and service sequence establish order, not hypothesis quality.
- Clear compile/official-verifier status. The prior adapter already exited
  nonzero on failure; this is a visibility improvement, not a false-success fix.
- Optional generic Java test runner using actual candidate classes and public
  API. No game-strategy fixtures or specific assertions are supplied. Tests are
  uninstrumented JVM checks, not engine/bytecode equivalence or coverage proof.
- Two public development opponents on two prospectively selected maps, both
  sides, fixed for every source version. No observer selects strategy or edits
  the candidate after launch.

The strict production evaluator gates remain unchanged. This native same-user
profile has procedural workspace restrictions, not per-agent filesystem/tool
confinement or hostile-tenant security. Prior observer artifacts remain outside
the fresh export and must not be read; their presence on the shared VM is not
concealed as a hard boundary. Fresh future evaluation material remains private
and unmaterialized until this competitor stops. Do not claim a complete access
audit when native tool history is unavailable.

## Budgets and gates

- Prelaunch engineering integration: **eight games maximum**, official tutorial
  lectureplayer against each public opponent on both maps/both sides, through
  the future note-required service. Source and note receipt precede submission.
  Exactly one submitted tutorial version. No hidden retries or extra calibration.
  The existing lectureplayer pin remains `57063ad07b2311c21c99ba7be100a55fcdb3de6b`.
- Gate: current code CI and local tests pass, runtime/source/map/build pins frozen,
  real cross-invocation note→submit→result→bounded-replay works, each integration
  game has complete terminal replay and both teams show active play. Test helper
  must work from a separate ordinary native tool invocation, not only inside the
  operator's Nix shell. Any infrastructure failure stops this protocol; preserve
  evidence, fix environment and make a new prospective record before further games.
- Requested fresh competitor `gpt-6.1-sol`, high effort, `fork_turns:none`.
  Distinguish requested/accepted settings from independent runtime attestation.
- Fresh source-empty export contains only public rules/API, generic helpers,
  disclosed development interface, kickoff and writable source/tests/work dirs.
  No prior bot, strategy review, results, observer plans or benchmark material.
- Competitor: **45minutes**, at most **eight submitted versions /64development
  games**,150 replay requests,24 bounded notes. Compilation rejection consumes
  a version but no game. Each match has120-second process timeout,512MiB heap;
  no aggregate CPU/disk/PID guarantee is claimed. Local Java checks use their
  separately documented bounded subprocess limits.
- Stop immediately for infrastructure failure, halted service or uncertain
  submission. No observer bot repair/coaching; subsequent session after an
  environment repair must be genuinely fresh and separately preregistered.
- Candidate selects a submitted immutable version itself, writes final evidence,
  stops. Observer verifies source/report hashes and finished native status,
  stops service, then releases independent evaluation acquisition gate.
