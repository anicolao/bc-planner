## One narrow change

[010's public validation stopped without a selection](2023-own-diagnostics-010-public-outcome.md).
A separately preregistered, one-attempt public diagnostic completed in122.407
seconds with a300-second cap and unchanged frozen inputs. This showed only that
120 seconds was insufficient for that execution; it did not establish the
original timeout cause, repair validation or evaluate competence.

Add trusted configuration `match_timeout=300`, uniformly for training and public
finalist validation. Missing configuration preserves the existing `timeout`
default. Only adapter `run` uses the new allowance: its engine and initial replay
summary are separately bounded by300 seconds **and the same remaining absolute
global deadline**. This is not600 additional seconds outside the trial clock.
Build, package and later replay-query requests retain `timeout=120` for their
child subprocesses, also clipped by the same absolute deadline; this is not a
total-request elapsed-time guarantee. The service
clips every child operation to remaining time, terminates/reaps expired children,
and does not start new games after stopping. The candidate cannot set these caps.

[bcenv PR23](https://github.com/anicolao/bcenv/pull/23), stacked on draftPR22,
changes trusted host service/configuration and launch-parity identity only.
The installed adapter, engine, Java runtime, replay projection and match settings
are unchanged. The same runtime closure is expected, not evidence of a missing
code deployment: host service source hashes are independently bound at launch.
This is a prospective reliability adjustment, not a randomized causal comparison.
