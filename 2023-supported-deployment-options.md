# BC2023 autonomous agent: supported setup options

Research checked: 20 October 2026 (UTC). This is a deployment proposal, not a provisioned or validated deployment.

## Recommendation and present gate

Prefer an existing, explicitly authorized Linux VM with administrator-provided cgroup v2 support. If none is available, the smallest practical paid fallback researched here is one DigitalOcean Basic Regular VM with 2 vCPUs and 4 GiB RAM. Both use the same deliberately small OpenAI Responses controller and isolated scrimmage-worker design below.

Neither route is currently ready: the available managed dot VM lacks the required delegated resource controls; no suitable authorized registered remote/saved coding environment is presently available. Its managed CLI/sandbox restrictions must remain intact. A native agent sharing the current filesystem does not provide the requested candidate isolation. New infrastructure, paid inference, credentials, and security configuration need separate user decisions and secure setup.

## The two options

1. **Existing authorized VM, preferred.** Ubuntu 24.04 LTS, x86-64, at least 2 vCPUs/4 GiB RAM, spare disk for a pinned toolchain, systemd and usable cgroup v2 CPU/memory/PID controllers. An administrator must provide an approved Docker Engine/runtime and resource configuration. The official Ubuntu documentation establishes platform support, not permission to use its package-manager recipe. This project requires agent-installed tooling to come from its pinned Nix flake; any new runtime package must be added through that reviewed flake, with no apt or direct-installer fallback. Host daemon/security configuration remains a separately approved administrator step. Incremental compute cost is $0 only if existing paid capacity is available without extra metered charges; API use still costs money. No such VM or authority is established today. Ubuntu 24.04 is a documented Docker Engine platform; Engine is community-supported software, not a Docker commercial support entitlement. [Ubuntu installation](https://docs.docker.com/engine/install/ubuntu/), [Engine support](https://docs.docker.com/engine/install/)

2. **DigitalOcean Basic Regular bundled Droplet, paid fallback.** Ubuntu 24.04 x86-64, 2 vCPUs, 4 GiB RAM, 80 GiB SSD; start with one active scrimmage. Published price: **$0.03571/hour, $24/month**, including bundled public IPv4; a 24-hour trial is **$0.85704 compute**, before taxes/API use. Choose the bundled Basic Regular plan, not a similarly sized v5 plan. Shared CPU performance varies, so evaluate game outcomes/bytecodes separately from noisy wall-time benchmarks. Region, account eligibility and live configuration availability remain unverified. [Official pricing](https://www.digitalocean.com/pricing/droplets)

   Billing runs until destruction, including while powered off. A 24-hour estimate is not an automatic spending cap. Export required results first; destruction permanently removes the VM and needs action-time confirmation. Avoid optional backups, snapshots, extra volumes and managed services for the trial. [Billing rules](https://docs.digitalocean.com/products/droplets/details/pricing/), [Destruction](https://docs.digitalocean.com/products/droplets/how-to/destroy/)

## Model connection with a closed tool surface

**Verified publicly documented configuration:** `model: "gpt-6.1-sol"`, `reasoning: {"effort":"high"}`, Responses API. Today's official model page explicitly lists this public model and effort. Its Chat Completions endpoint does not support tool calling. This corrects the earlier provisional status of the name, but does not establish this user's API access, billing, credentials, rate limits or equivalence to the internal agent harness. Verify an authenticated minimal request only after authorization. [Model documentation](https://developers.openai.com/api/docs/models/gpt-6.1-sol)

Use a small trusted controller, not an embedded CLI with inherited host capabilities. It submits an immutable, versioned array containing only application functions, for example `workspace_read`, `workspace_write`, `submit_scrimmage` and `read_scrimmage_result`. Set `strict: true`, reject additional properties, and set `parallel_tool_calls: false`. Strict schemas constrain format; the controller must separately enforce allowed paths, byte limits, job counts and semantic permissions. Responses function calls are requests for application-side execution, so the dispatcher can reject every unknown name and never enable built-in shell, web, MCP, connectors, tool search or dynamic registration. This closed surface is a property of our application design, not a claim about every agent framework. [Function calling](https://developers.openai.com/api/docs/guides/function-calling)

The API credential lives only in the trusted controller's secret configuration under a separate service identity. Never include it in model context, candidate environment, image, mount, Git history or tool result. Candidate builds run inside the same resource boundary as matches, with preloaded pinned dependencies and no network. The controller has no general model-callable shell or direct model-callable Docker socket; a narrow trusted broker accepts bounded source artifacts and fixed job configurations. Server-side secret storage follows the API guidance. [Authentication](https://developers.openai.com/api/reference/overview)

## Worker boundary and starting limits

Proposed starting values below require a BC2023 compatibility/performance test; they are not measured capacity claims.

- **Aggregate process-tree resources:** one fresh job cgroup, including compilation, Java, subprocesses and threads; 1 CPU bandwidth, 2 GiB memory, no swap, 256 tasks. Docker flags include `--cpus=1 --memory=2g --memory-swap=2g --pids-limit=256`. Inspect effective cgroup settings before admitting work; fail closed when unsupported. Do not substitute per-process `ulimit` for aggregate controls. [Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/), [PID option](https://docs.docker.com/reference/cli/docker/container/create/)
- **Lifetime CPU and cleanup:** CPU quota limits rate, not total consumed CPU-seconds. The trusted watchdog reads aggregate `cpu.stat` and kills the whole job cgroup at a proposed 60 CPU-seconds or 120 seconds elapsed, whichever is first. Polling/termination has overshoot; measure and publish that tolerance instead of promising an exact instantaneous cutoff. `cgroup.kill` covers descendants and concurrent forks. Keep the watchdog outside the job, deny candidate cgroup writes and real-time scheduling, and verify the cgroup is empty before reuse. [Kernel cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- **Writable space:** read-only image/root; source and engine inputs read-only; only size-capped scratch mounts: `/work` 512 MiB, `/tmp` 64 MiB, `/dev/shm` 16 MiB. Bound scratch inode counts as well. No writable host bind mounts or candidate-chosen mounts. These tmpfs allocations also consume the memory allowance; they are not an additional 592 MiB RAM entitlement. [Docker tmpfs](https://docs.docker.com/engine/storage/tmpfs/), [Kernel tmpfs sizing](https://cdn.kernel.org/doc/html/latest/filesystems/tmpfs.html)
- **Persistent output/disk:** disable Docker job log persistence with `--log-driver=none`; stream at most 4 MiB diagnostic output per job and accept at most 32 MiB validated replay/result data per job. For a 20-job trial, reserve at most 720 MiB for those outputs and stop before exceeding it. Give the nonprivileged artifact writer a 1 GiB/10,000-inode hard quota. Put Docker data, worker outputs and broker logs on an administrator-prepared fixed-size 10 GiB filesystem; cap related system logs separately and fail closed on exhaustion. Verify pinned images fit before launch. Scratch limits alone do not bound host logs or image accumulation. Pre-pull only fixed images; do not accept candidate Dockerfiles or arbitrary pulls. [Logging behavior](https://docs.docker.com/engine/logging/configure/), [Filesystem hard quotas](https://www.kernel.org/doc/html/latest/filesystems/quota.html)
- **Confinement:** nonroot job UID; `--network=none`; no privileged mode, host PID/network namespaces, Docker socket or secrets; drop all capabilities; no-new-privileges; retain and review seccomp/AppArmor; immutable harness; reject path escapes/symlinks and oversized archives. Keep the Docker daemon under trusted administrative control. Docker defaults alone are insufficient for this proposal. [Container controls](https://docs.docker.com/engine/containers/run/), [Docker security](https://docs.docker.com/engine/security/)

The stated threat model trusts the outer kernel/platform and excludes kernel zero-days and a malicious operator. Hardened containers can be assessed under that model against adversarial ordinary candidate code. A separate, secret-free worker VM is useful additional defense, not a prerequisite implied by shared-kernel isolation alone. It would need separate cost/configuration approval. Rootless Docker is an alternative only after confirming systemd/cgroup v2 delegation: its documentation warns resource flags can be ignored when prerequisites are absent, and CPU delegation is not necessarily present by default. [Rootless resource prerequisites](https://docs.docker.com/engine/security/rootless/tips/)

## Bounded trial budget, not authorization

Published Standard short-context Sol pricing is $2/M input tokens, $10/M output tokens; cache writes are $2.50/M. No Fast/Ultrafast, regional uplift or built-in paid tools are assumed. [API prices](https://developers.openai.com/api/docs/pricing)

Example admission envelope: **20 total API requests, including retries**, each at most 16,000 input tokens and 8,000 generated tokens. Reserve against the full request before sending; stop rather than auto-increasing limits. A conservative calculation treating all input at the cache-write rate is 0.32M × $2.50 + 0.16M × $10 = **$2.40 API**. The output ceiling includes reasoning and non-visible generated tokens. Exact input admission must include instructions, schemas, history and tool outputs. [Token accounting](https://developers.openai.com/api/docs/guides/token-counting)

That gives **$3.26 estimated usage for API plus 24 hours of the fallback VM**, before taxes, extra services and any account-opening/prepaid-credit requirements. Existing-VM incremental usage is at most $2.40 under these assumptions. Small token ceilings may truncate high-effort reasoning; this is an integration trial, not evidence of competitive strength. A real all-in spending limit must be approved after billing requirements are visible. Application reservations and request counts are required; do not assume a dashboard alert is a hard stop.

## Exact decisions and handoffs before implementation

1. **Environment:** user chooses an existing authorized VM or explicitly approves a named provider/region/plan and all-in trial limit. For an existing VM, its owner supplies the supported managed/registered environment, sufficient resources and explicit permission for container/resource/security setup. Current managed-environment restrictions are not changed.
2. **Supported attachment:** the user/platform registers or makes the VM available as a supported remote/saved coding environment. Recheck the environment list, then create the execution task through the platform's supported cloud-task route. Do not copy SSH credentials ad hoc or use the user's Mac. No working attachment is established by this report.
3. **API and secrets:** user approves the model/provider and API spending, establishes any needed account/billing, and enters credentials through secure setup outside chat. Credential creation/persistent access and security changes require their applicable confirmation. The configured secret remains inaccessible to candidates; do not ask the user to paste it into chat.
4. **Administrator setup:** after the applicable explicit authorization, provide the approved runtime, configure broker/service identities, cgroups, quotas and confinement, pin all agent-installed tooling through the repository Nix flake, and record effective settings. Do not substitute an unreviewed apt/direct-installer workflow. If the platform cannot expose the required controls, stop and request a suitable supported environment; no sandbox bypass.
5. **Acceptance gate:** test fork/thread floods, aggregate memory, CPU-bound descendants, timeout cleanup, file/inode floods, excessive stdout, path traversal, credential/host-file/network access, tampered tool calls and supervisor restart recovery. Then run one known deterministic BC2023 match and a bounded API tool-call smoke test. Keep live autonomous runs disabled until these pass.
6. **Trial/end condition:** agree on run count, token budget, retention and deadline. At completion, report actual costs/resources and export approved artifacts. For a new VM, obtain the required deletion confirmation and verify destruction to stop billing; powering off is insufficient.

No paid resource, account, credential, security setting or remote connection was created for this research.
